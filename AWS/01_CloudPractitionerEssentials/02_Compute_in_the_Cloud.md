## Amazon EC2 の概要
### 再掲：コーヒーショップの例  
従業員はクライアント/サーバーモデルのサーバーにあたり、クライアントがサーバーにリクエストを送信し、サーバーが処理を行い、その後、応答を返すというしくみ  
  
アプリケーションをホストし、ビジネスに必要な処理能力を提供するには、その土台となる高いコンピューティング性能が必要  
→ AWS を使用する場合、そのようなサーバーは EC2 インスタンスと呼ばれる。  

### EC2 をコンピューティングに使うメリット
- 非常に柔軟でコスト効率が高く、迅速に運用できる。  
オンプレミスのリソースで運用を開始するには、時間とコストがかかるが、EC2 を使用すれば、もっと手軽に始められる。難しい作業は、AWSがお客様に代わって処理する。  

- EC2 インスタンスの料金は実行中のインスタンスに対してのみ発生し、停止または終了したインスタンスには発生しない。

### マルチテナント
EC2 インスタンス ＝ 仮想マシン (VM)  
マルチテナント ＝ VM が 基盤となる物理ホストマシンを他の複数のインスタンス（実体）と共有する、という概念  
マルチテナント環境 → 各 VM が互いに分離されつつも、ホストが提供するリソースを共有できるようにする必要がある。  

***
このリソースの共有と分離は、ホストマシン上で実行されるハイパーバイザーと呼ばれるソフトウェアによって行われます。EC2 では、基盤となるホスト、ハイパーバイザー、インスタンス間の分離は AWS が管理する。そのため、お客様がこの部分を管理することはありません。それでも、マルチテナントの基本的な概念を把握しておくことは重要。
***

### マルチテナントの基本的な概念_EC2 インスタンスをプロビジョニング（準備）する場合
- Windows または Linux をベースにしたオペレーティングシステム (OS) を選択可能  
→ 数千台の EC2 インスタンスをオンデマンドでプロビジョニングし、さまざまなオペレーティングシステムと構成を組み合わせることで、ビジネスの多様な用途に対応できる。  
― インスタンスで実行するソフトウェアを自由に設定することも可能。  
- インスタンスのサイズ変更も可能。  
  インスタンスの垂直スケーリング：サーバー容量限界などに伴い、インスタンスにメモリやCPUを追加すること
- EC2 のネットワーク設定も制御可能。  
→ サーバーに送信するリクエストの種類や、そのアクセスをパブリックにするかプライベートにするかを決定できる。
***
VM の概念は新しいものではない。AWS のコンピューティングをサービスとして利用するモデルにより、サーバーの調達がより便利になり、コスト効率も向上した。

## Amazon EC2 インスタンスタイプ
### 例：コーヒーショップのさまざまな種類のコーヒーマシン
- お客様は選択肢が多いことを好む  
  → 全1 種類のコーヒーマシンだけでは不足  
  → 効率的に運営するため、注文ごとに適切なコーヒーマシンを使用することが重要

## EC2 インスタンスをデプロイすること  
- AWS 環境 → 多様な目的に応じてさまざまなタイプのインスタンスがある
- インスタンスタイプはインスタンスファミリーに分類され、各ファミリーでは、CPU、メモリ、ストレージ、ネットワークの容量のさまざまな組み合わせが提供される  
  → そのため、ワークロードに適したインスタンスを選択することで、特定のタイプのタスクを柔軟に最適化可能。

※  `インスタンスタイプ = インスタンスファミリー × サイズ`  というイメージ

### インスタンスファミリー
#### 汎用インスタンス
- コンピューティング、メモリ、ネットワークリソースがバランスよく提供される
- ウェブサービスやコードリポジトリなど、さまざまなワークロードに使用可能
- ワークロードのパフォーマンスが事前にわからない場合の最初の選択肢としても適している。

#### コンピューティング最適化インスタンス
- 計算集約型のタスクに最適。  
  ゲームサーバー、ハイパフォーマンスコンピューティング、機械学習タスク、さらには科学モデリングなど。

#### メモリ最適化インスタンス
- メモリ集約型のタスクに適している
- 大規模なデータセットをメモリで処理するワークロードに対して高いパフォーマンスを発揮。

#### 高速コンピューティングインスタンス
- 浮動小数点数の計算、グラフィックス処理、データパターンマッチングなどに適している。  
  → ハードウェアアクセラレーターを使用しているため
  - ハードウェアアクセラレーター = CPU 上で動作するソフトウェアよりも効率的に動作するコプロセッサ。

#### ストレージ最適化インスタンス
- ローカルに保存されたデータに対して高いパフォーマンスを必要とするワークロードに最適。

### インスタンスサイズ
- インスタンスタイプを決定したら、次は適切なインスタンスサイズを選択する。
- パフォーマンス以外にも考慮してほしいのはコスト。
- 大きなインスタンスほど、より多くの CPU、メモリ、ストレージを利用可能な一方、コストも高くなる。
- ニーズと予算に合ったバランス → 最適なパフォーマンスを得るために適切なインスタンスサイズを選択でき、必要のないリソースに無駄なコストを支払わずに済む。

### 最大の利点 = 特定のインスタンスのタイプやサイズを永久に使い続ける必要がないこと
最初に選択したインスタンスでは、必要なパフォーマンスが得られないことに気付くかもしれません。それはまったく問題ありません。  
インスタンスは変更可能。クラウドを利用すると、とても迅速に変更できるので、その利点を活用しましょう。

## AWS リソースをプロビジョニングする方法
- AWS では、API コールを使用して操作する。
- API ⁼ Application Program Interface の略称
  → AWS のサービスを操作するためにあらかじめ定義された方法を示すもの
- API の呼び出し（ = API コール）により、リソースのプロビジョニング、設定、管理を行うことができる。

### AWS API を呼び出す方法
- 主な方法は 3 つ。AWS マネジメントコンソール、AWS コマンドラインインターフェイス (CLI)、AWS ソフトウェア開発キット (SDK) のいずれかを使用する。

#### ① AWS マネジメントコンソール
- ブラウザベースのコンソール
- リソースを視覚的に、わかりやすい方法で管理できる
- サービスを初めて利用し、知識を深めていくのに最適
- テスト環境のセットアップ、AWS 請求書の確認、リソースのモニタリング、技術以外のタスクの管理にも役立つ
- ほとんどの場合、AWS について学ぶ際に最初に利用するのはコンソール（この方法）
- ただし、複数のサービスを管理するには非効率で、タスクの自動化にも不適切な方法

#### ② AWS CLI
- AWS CLI を使用し、ターミナルから AWS API を呼び出す
- Windows、macOS、Linux のコマンドラインから AWS の複数のサービスを直接管理可能
- スクリプトを使用して、EC2 インスタンスの起動などのタスクを自動化できる

#### ③ AWS SDK
- Python などのさまざまなプログラミング言語を使用して AWS リソースを操作できる
- AWS SDK で提供されているさまざまなプログラミング言語用の API を使用して、アプリケーションに AWS のサービスを簡単に統合できる


## デモ: Amazon EC2 インスタンスを起動する
### AMI（Amazon マシンイメージ） のコンポーネント
#### AMI の構成 
- オペレーティングシステム
- ストレージのセットアップ
- アーキテクチャタイプ
- 起動のためのアクセス許可
- その他のインストール済みソフトウェア
1 つの AMI を使用して、まったく同じ設定の EC2 インスタンスを複数起動可能。
### AMI を使用する 3 つの方法
#### ① カスタム AMI
ニーズに合わせた設定とソフトウェアを使用してカスタム AMI を構築する方法
#### ② 設定済みの AWS AMI
一般的なオペレーティングシステムとソフトウェア用にセットアップされた、設定済みの AWS AMI を使用する方法
#### ③ AMI を購入
AWS Marketplace から AMI を購入する方法

### AMI の再現性
- AMI では、すべての新しいインスタンスに対して一貫した環境が提供され、再現性が確保される
- 同一の設定でデプロイは自動化されているため、開発環境とテスト環境との間で一貫性が保たれる
  ↓　↓  
これらはスケーリング時に役立ち、エラーを減らし、大規模環境の管理を効率化することができる

## Amazon EC2 の料金
### AWS の料金オプション
#### オンデマンドインスタンス
- 使用したコンピューティング性能に対してのみ料金が発生
- 前払いや長期契約の必要がない
#### リザーブドインスタンス
- 最大75％の割引が受けられる
- 特定のインスタンスファミリーとAWSリージョンを使用し、予測可能なワークロードに対して1年または3年の利用をコミットする必要がある
#### スポットインスタンス
- 最大90％割引で予備のコンピューティング性能に入札できる
- 使用していない Amazon EC2 容量を活用する
- AWSがインスタンスを回収する際にはサービスが中断される可能性がある
#### Savings Plans
- 様々なインスタンスタイプやサービスで最大72％の割引が受けられる
- 1年または3年にわたって一定の使用量をコミットすることが必要
#### 専有ホスト
- 物理サーバー全体をその顧客専用に予約できる
- 完全な制御が可能になるため、厳しいセキュリティ要件やライセンス要件があるワークロードに最適
#### ハードウェア専用インスタンス
- 顧客アカウント専用のハードウェアで実行されるインスタンスに対し、料金を支払う
- AWSの他顧客との物理的な分離が可能

### コスト最適化の詳細
#### Saving Plans
適した要素：予測可能なワークロード
#### キャパシティーの予約
適した要素：厳しい性能要件がある重要なワークロード
- 特定のアベイラビリティーゾーンでコンピューティング性能を予約できる
- 予約は、使用の有無にかかわらずオンデマンド料金が発生。ただし、実行したインスタンスのみが支払い対象。
 
#### リザーブドインスタンスの柔軟性
適した用途：使用量が一定で予測可能なワークロード
- 最大75％の割引が受けられる
- 割引は複数のアベイラビリティーゾーンに適用されるため、リソースを分散して耐障害性を強化できる

## Amazon EC2 のスケーリング
### ポイント
#### スケーラビリティ（拡張性）
システムの能力を時間と共に拡張できること
#### 伸縮性（弾力性）
リソースを動的にオンデマンドで調整すること

### スケーラビリティ（拡張性）
- システムやビジネスの成長、または負荷の増加に合わせて、性能や処理能力を拡張できる能力
#### スケールアウト
- 数を増やす  
  例：計画的にサーバーの台数を増やす
#### スケールアップ
- 性能を上げる  
  例：サーバー自体の性能を上げる

### 伸縮性
需要の変動に応じて、ITリソース（容量や台数）を動的かつ自動的に増減させる能力

### Amazon EC2 Auto Scaling
- アプリケーションの需要の変化に応じて EC2 インスタンスの数を自動的に調整し、可用性を向上させる
#### 動的スケーリング
需要の変動に応じてリアルタイムで調整する
#### 予測スケーリング
予測された需要に基づいて、適切な数のインスタンスを事前にスケジュールする

## Elastic Load Balancing を使用してトラフィックを転送する
### Elastic Load Balancing (ELB)
- EC2 インスタンスなどの複数のリソースにアプリケーションの受信トラフィックを自動的に分散  
  → アプリケーションのパフォーマンスと信頼性を最適化する。
- EC2 インスタンスの数はトラフィックの需要に応じて変動するため、受信リクエストはまずロードバランサーに送られる。そこから、利用可能なインスタンス全体にトラフィックが均等に分散される。
  - ロードバランサー：Auto Scaling グループに到達するウェブトラフィックすべての単一接続先として機能する。

### AWS の Elastic Load Balancing (ELB) の利点
#### 効率的なトラフィック分散
複数の EC2 インスタンスにトラフィックが均等に分散されることで、1 台のインスタンスが過負荷にならないようにし、リソースの利用を最適化できる。
#### オートスケーリング
トラフィックに応じてスケールし、バックエンドインスタンスの追加や削除に伴う需要の変化に自動的に対応することで、シームレスな運用を実現する。
#### 管理の簡素化
- フロントエンド層とバックエンド層が疎結合化され、手動による同期が減る。
- メンテナンス、更新、フェイルオーバーが処理されるため、運用上のオーバーヘッドが軽減される。
### Amazon EC2 Auto Scaling と ELB の関係
- ELB と Amazon EC2 Auto Scaling は異なるサービス
- これらを連携して動作することで、アプリケーションのパフォーマンスを向上させ、高可用性が確保される
- この連携により、Amazon EC2 で実行中のアプリケーションは一貫したパフォーマンスを維持しながら効果的にスケールできる。
- Amazon EC2 Auto Scaling によってインスタンスの数が調整され、ELB によってトラフィックがインスタンス間で均等に分散される。
  
### ELBのルーティング方法
#### ラウンドロビン
利用可能なすべてのサーバーにトラフィックを周期的かつ均等に分散する
#### 最小接続
アクティブな接続数が最も少ないサーバーにトラフィックをルーティングすることで、負荷を均等に保つ
#### IPハッシュ
クライアントの IP アドレスに基づいてトラフィックを常に同じサーバーに送信する
#### 最小応答時間
応答時間が最も速いサーバーにトラフィックを送信し、レイテンシーを最小限に抑える

## メッセージングとキューイング
### 密結合アーキテクチャと疎結合アーキテクチャの違い
#### 🤔密結合：モノリシックアプリケーション
- アプリケーション内のコンポーネント同士が『密』の状態
- 1つのコンポーネントに障害が発生すると、他のコンポーネントの障害を引き起こし、アプリケーション全体が停止する可能性がある
#### 😁疎結合：マイクロサービスアーキテクチャ
- アプリケーションの可用性と耐障害性、柔軟性と信頼性が向上
- アプリケーション内のコンポーネント同士が『独立性の高い』状態
- 1つのコンポーネントに障害が発生しても、他のコンポーネントは正常に機能し続けることができる
- コンポーネント間の通信はそのまま維持され、1 つのコンポーネントの障害がシステム全体に影響することはない
### ポイントざっくり
#### Amazon EventBridge
- イベントを見て「これは誰に渡すべきか」を振り分ける交通整理役
- ルールに合うイベントをターゲットへ送るイベント駆動型
#### Amazon SQS（Amazon Simple Queue Service）
- メッセージを一旦ためて、受け取り側が取りに来るまで待つ順番待ち箱
- プル型
#### Amazon SNS（Amazon Simple Notification Service）
- 受け取ったメッセージを登録者全員に一斉配信する拡声器
- プッシュ型
